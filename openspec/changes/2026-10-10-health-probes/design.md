# 设计

## 模块与请求边界

- `HealthController` 继续由 `HealthModule` 独立提供，不把探针逻辑放入业务模块。
- `GET /health/live` 只调用内存中的 `HealthService.liveness()`，不创建数据库请求。
- `GET /health/ready` 调用 `HealthService.checkReadiness()`，复用现有 `PrismaService.$queryRaw\`SELECT 1\`` 检查关键依赖。
- 现有 `GET /health` 委托到就绪检查，保持已有调用方和响应结构不变。
- `PrismaService` 不在模块初始化阶段强制连接数据库，改为首次查询时懒连接，确保数据库故障时应用仍能启动并响应存活探针。

## 故障模型与恢复边界

- 进程事件循环仍能处理请求但数据库不可用：存活探针成功，就绪探针返回 503，部署系统应停止向该实例分发流量。
- 进程无法处理 HTTP 请求：两个探针都无法提供有效结果，由外部运行时决定是否重启。
- 数据库恢复后：就绪探针重新返回 200，实例是否重新加入流量由部署系统执行；本应用不维护流量注册表。
- 应用启动但数据库尚未恢复：存活探针仍可返回 200；业务请求和就绪探针按各自的数据库访问结果失败或恢复。

## 选择与取舍

- 使用两个固定 HTTP 路径而不是在响应体中增加模式参数，使编排配置和人工检查都能直接表达意图。
- 保留 `/health` 是兼容性取舍；新部署应分别使用 `/health/live` 和 `/health/ready`，不再把旧路径当作两种探针的替代品。
- `SELECT 1` 只证明数据库连接可用，不测量业务延迟、连接池余量或完整事务能力；这些属于后续压测和 SLO 学习内容。
- 懒连接只改变启动时机，不改变数据库是业务请求的必要依赖；生产入口的 migration 失败仍应阻止部署继续接流量。

## Fastify 兼容性

探针仍是普通 NestJS Controller 路由，不依赖 Express API；现有 Fastify `app.inject()` E2E 测试验证路径、状态码和响应体。
