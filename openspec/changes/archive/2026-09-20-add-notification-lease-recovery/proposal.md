# 通知任务租约恢复

## Why

当前通知处理器使用条件更新把任务从 `pending` 抢占为 `processing`。如果实例在抢占后、完成通知前崩溃，任务会永久停留在 `processing`，后续实例无法判断它是否仍在工作，也就无法恢复异步流程。

本次增量开启高并发与分布式协作学习，目标是理解任务租约、实例故障、重复消费和幂等之间的关系：任务的持久化状态仍由 PostgreSQL 负责，租约过期只表示允许其他实例重新尝试，不表示上一次处理一定没有副作用。

## What Changes

- 为通知任务增加可空的 `leaseUntil` 字段和租约索引。
- 认领任务时写入短租约；认领条件同时支持新的 `pending` 任务和已过期的 `processing` 任务。
- 成功、失败和关闭流程清理租约，避免已结束任务被误判为可恢复任务。
- 增加租约恢复的单元测试和 PostgreSQL 集成测试，并在关键并发边界补充中文学习注释。
- 更新学习路线，记录租约恢复的故障模型、容量假设和后续 Redis/BullMQ 边界。

## Non-Goals

- 不引入 Redis、BullMQ、分布式锁或微服务拆分。
- 不实现租约续期、任务优先级、人工重放接口或跨实例协调协议。
- 不承诺恰好一次处理；通知唯一约束和 `skipDuplicates` 仍是重复消费时的幂等保护。

## Impact

- 模块：调整 `NotificationsModule` 中的 `NotificationProcessor` 任务认领和结果状态更新。
- 数据库：为 `notification_jobs` 增加 `lease_until` 字段及状态/租约索引。
- HTTP：不改变现有 HTTP 契约，任务状态接口仍只负责提交 outbox 工作。
- 测试：增加 Processor 租约回收单元测试和数据库集成测试。
- 运行边界：租约时长固定为 30 秒，适用于当前轻量通知处理；未来应根据处理耗时分布和实例故障恢复目标重新配置。
